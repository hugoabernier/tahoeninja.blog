Building a Multi-Step Form with SPFx and React Hooks

Multi-step forms reduce cognitive load and improve completion rates. Here's a type-safe, accessible implementation for SharePoint Framework.

🥷
Hugo Bernier
May 28, 2025 · 8 min read
SPFx TypeScript

When building enterprise SharePoint solutions, multi-step forms often feel like the right call — but the implementation details can make or break the user experience for the people who interact with these forms every single day.

The psychology is simple: presenting 20 fields at once is intimidating. Breaking them into logical groups — identity, preferences, confirmation — reduces perceived complexity and keeps users moving forward.

Modeling the State

Keep all form state in a single top-level object. This makes the final submission straightforward and eliminates the class of bugs where navigating back discards earlier data.

Type safety tip: Use Partial<FormData> as the initial state. TypeScript then knows every field may be undefined until the user fills it in — no need for explicit null checks or empty-string defaults.

MultiStepForm.tsx TSX 
interface FormData {
  displayName: string;
  email: string;
  notifyByEmail: boolean;
  frequency: 'daily' | 'weekly' | 'monthly';
}

const MultiStepForm = () => {
  const [step, setStep] = useState(0);
  const [data, setData] = useState<Partial<FormData>>({});

  const update = <K extends keyof FormData>(k: K, v: FormData[K]) =>
    setData(prev => ({ ...prev, [k]: v }));

  return (
    <Wizard step={step}
      onNext={() => setStep(s => s + 1)}
      onBack={() => setStep(s => s - 1)}>
      {step === 0 && <IdentityStep data={data} onChange={update} />}
      {step === 1 && <PrefsStep data={data} onChange={update} />}
      {step === 2 && <ConfirmStep data={data} />}
    </Wizard>
  );
};

Step Validation

Validate on step transition, not on submit. Surfacing errors early keeps the user's attention focused on the fields that need fixing — not a wall of errors at the end of a multi-step process they can't easily navigate back through.

Keep validators as pure functions. They become trivial to unit-test in isolation — no component mounting, no mocking, no ceremony. Just input in, boolean out.
