Building a Multi-Step Form with SPFx and React Hooks

Multi-step forms feel complex to build — but with the right state model and a touch of TypeScript discipline, they come together cleanly.

🥷
Hugo Bernier
May 28, 2025
8min read
4sections

When building enterprise SharePoint solutions, multi-step forms often feel like the right call — but the implementation details can make or break the user experience for the people who interact with these forms daily.

The psychology is well-established: presenting twenty fields at once is intimidating. Breaking them into logical groups reduces perceived complexity and keeps users in a forward-moving flow. But doing this well in SPFx takes some care.

Modeling the State

Keep all form data in a single object at the top level of your wizard component. This eliminates an entire class of bugs — the kind where navigating back to a previous step discards what the user already entered.

🌱
Design decision

Using Partial<FormData> as the initial state means TypeScript knows that fields may be undefined until the user fills them in. This beats both null and empty strings for correctness.

T
MultiStepForm.tsx 
interface FormData {
  displayName: string;
  email: string;
  department: string;
  notifyByEmail: boolean;
  frequency: 'daily' | 'weekly' | 'monthly';
}

const MultiStepForm: React.FC = () => {
  const [step, setStep] = useState(0);
  const [data, setData] = useState<Partial<FormData>>({});

  // A generic updater — TypeScript enforces key/value compatibility
  const update = <K extends keyof FormData>(
    key: K, value: FormData[K]
  ) => setData(prev => ({ ...prev, [key]: value }));

  return (
    <Wizard step={step}
      onNext={() => setStep(s => s + 1)}
      onBack={() => setStep(s => s - 1)}>
      {step === 0 && <IdentityStep data={data} onChange={update} />}
      {step === 1 && <PrefsStep data={data} onChange={update} />}
      {step === 2 && <ConfirmStep data={data} />}
    </Wizard>
  );
};

Accessible Step Navigation

Step indicators are often treated as decoration, but they carry real semantic weight. A screen reader user needs to know where they are in a process — and the browser won't tell them unless you do.

⚠️
Accessibility pitfall

Don't rely on visual position alone. Add aria-current="step" to the active indicator and wrap the container in role="list" so the count is announced automatically.

Use a live region to announce step transitions. When the view changes, update the live region text: "Step 2 of 3: Notification Preferences". This costs ten lines of code and saves your users genuine confusion.
